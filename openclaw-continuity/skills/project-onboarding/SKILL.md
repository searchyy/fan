# 新项目上手流程

## 核心原则

**先搞懂，再动手。** 不要假设任何参数格式、编码方式、调用顺序。每一步都要有依据。

## 强制调研清单

参与任何新项目前，必须按顺序完成以下步骤。每步标记 ✅ 后才能进入下一步。

### Phase 1: 信息收集

#### 1.1 官方文档全读

- [ ] 官网所有页面（包括 FAQ、Docs、About）
- [ ] GitHub README、Wiki
- [ ] 官方 Skill/SDK 文档（如有）
- [ ] 白皮书或 Litepaper

#### 1.2 合约源码分析

- [ ] 找到所有相关合约地址
- [ ] 查 Etherscan/Basescan 是否已验证源码
- [ ] 如果是 Proxy，找到 implementation 地址
- [ ] 读关键函数的参数类型和编码方式
- [ ] 特别注意：参数是 `uint256` 还是 `bytes32`？需要 hash 还是原始值？

#### 1.3 前端代码逆向

- [ ] 查看官方前端 JS 中的合约调用方式
- [ ] 找到 ABI 定义
- [ ] 找到参数编码逻辑
- [ ] 找到 config.js 或类似配置文件中的合约地址

#### 1.4 链上数据验证

- [ ] 找到已成功参与的地址（排行榜、事件日志）
- [ ] 查看他们的交易 input data
- [ ] 对比他们的参数格式和自己的理解是否一致
- [ ] **这一步是最关键的验证环节，不能跳过**

### Phase 2: 小规模验证

#### 2.1 单账号测试

- [ ] 用 1 个账号完成完整流程
- [ ] 确认交易成功（不只是 tx 成功，还要确认业务逻辑成功）
- [ ] 等待结算/结果，确认拿到预期产出（奖励、积分、NFT 等）
- [ ] 如果没拿到，排查原因后重试

#### 2.2 对比验证

- [ ] 将自己的提交数据与成功者的数据逐字节对比
- [ ] 确认编码方式、参数顺序、数值格式完全一致

### Phase 3: 批量部署

只有 Phase 2 确认成功后才能进入此阶段。

- [ ] 编写自动化脚本
- [ ] 多账号批量执行
- [ ] 设置监控和通知
- [ ] 记录所有关键参数到 memory 文件

## 常见陷阱

### 参数编码

| 陷阱 | 说明 |
|------|------|
| hash vs 原始值 | 合约可能期望直接整数而非 keccak256 hash |
| 大小写敏感 | X handle、用户名等可能需要小写 |
| 字节填充 | `bytes32` 参数需要左填充零 vs 右填充零 |
| ABI 编码 | `abi.encode` vs `abi.encodePacked` 结果不同 |

### 流程遗漏

| 陷阱 | 说明 |
|------|------|
| commit-reveal | 提交 hash 后还需要 reveal 原始值 |
| approve 前置 | ERC20 操作前需要 approve |
| 注册前置 | 某些操作需要先注册/质押 |
| claim 手动 | 奖励不会自动到账，需要手动 claim |

### 时序问题

| 陷阱 | 说明 |
|------|------|
| 重复提交 | 同一轮不能提交两次 |
| 截止时间 | 超时提交会被拒绝 |
| 结算延迟 | 结果可能不是实时的 |

## 调研报告模板

完成调研后，在 memory 中记录：

```markdown
## [项目名] 调研报告

### 基本信息
- 官网:
- 合约地址:
- 链:

### 参与流程
1. [步骤1]
2. [步骤2]
...

### 关键参数
- 函数签名:
- 参数编码方式:
- 示例 input data:

### 验证结果
- 测试账号:
- 测试交易:
- 是否成功拿到产出: ✅/❌

### 自动化方案
- 脚本路径:
- 定时方式:
- 监控方式:
```

## 失败后的排查顺序

1. 对比成功者的 tx input data
2. 检查参数编码方式
3. 检查是否遗漏前置步骤
4. 检查合约是否是 proxy，ABI 是否匹配 implementation
5. 检查链上状态（是否已注册、是否已提交、余额是否足够）
