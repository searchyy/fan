# 协调者模式 (Orchestrator Pattern)

主 agent 做判断和决策，子 agent 做执行。省 token，提质量。

## 核心原则

**你是协调者，不是工人。** 规划、拆解、审查是你的工作。大量编码、批量处理交给子 agent。

## 三阶段工作流

### 1. 规划 (Plan)

收到复杂任务时，先拆解：

```
任务：构建一个 API 服务
拆解：
  1. 设计 API 接口规范 (你来做)
  2. 实现路由和控制器 (子 agent)
  3. 实现数据库模型 (子 agent)
  4. 编写测试 (子 agent)
  5. 审查整合 (你来做)
```

**规划清单：**
- 明确最终目标和验收标准
- 识别可并行的子任务
- 为每个子任务写清晰的 spec（输入、输出、约束）
- 决定哪些需要你亲自做（判断类）、哪些可以分发（实现类）

### 2. 实现 (Execute)

通过 `sessions_spawn` 分发子任务：

```
sessions_spawn(
  task: "根据以下 spec 实现用户认证模块：[详细 spec]",
  label: "auth-module"
)
```

**分发原则：**
- 每个子任务的 spec 必须自包含，不依赖对话上下文
- 明确输出格式和文件路径
- 可并行的任务同时 spawn
- 单个子任务不超过一个明确目标

**适合分发的工作：**
- 批量代码生成 / 样板代码
- 文件格式转换 / 数据处理
- 独立模块实现
- 测试编写
- 文档生成

**不适合分发的工作：**
- 架构决策
- 需要用户确认的选择
- 涉及安全/敏感操作
- 需要完整项目上下文的判断

### 3. 审查 (Review)

子 agent 完成后，审查输出：

- 是否符合 spec 要求
- 边界情况是否处理
- 代码风格是否一致
- 模块间接口是否对齐
- 有无安全隐患

审查发现问题 → 修正或重新分发，不要自己重写整个实现。

## 操作纪律

### Checkpoint 规则
- 每完成一个子任务，汇报进度
- 不要连续做 5 件事再一起汇报
- 格式：`[3/5] 用户模块完成，开始支付模块`

### 大操作预警
- 读取大文件前先说明：「这个文件 2000 行，正在读取」
- 批量修改前先确认范围
- 预计耗时长的操作提前告知

### 静默限制
- 复杂操作中定期更新状态
- 遇到阻塞立即汇报，不要卡住不说
- 子 agent 超时未返回，主动检查并汇报

## 指令精确性

给子 agent 写 spec 时：

**差：** "写一个用户模块"
**好：** "在 /src/models/user.js 创建 User 模型，包含 name(string), email(string, unique), createdAt(date) 字段，使用 Mongoose，导出模型"

**差：** "优化这段代码"
**好：** "将 getUserList 函数的数据库查询从 N+1 改为 JOIN，保留现有的错误处理逻辑不变"

## 成本意识

- 判断类工作（架构、审查、决策）→ 主 agent
- 实现类工作（编码、转换、批量）→ 子 agent
- 简单任务直接做，不值得 spawn 的开销
- 预估：spawn 一个子 agent ≈ 一次完整对话的成本，任务太小不划算
